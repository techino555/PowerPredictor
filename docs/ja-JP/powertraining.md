# モデルの訓練(戦闘力モデルの確立)

768次元のDINOv3 Embeddingから正確な戦闘力スコアを弾き出すためのモデルの訓練手順と、その背景にある設計思想について解説する。

## モデルの訓練目的と役割分担

このモデル作成を通じて機械学習の勉強を始めた頃は、「モデルとはプログラムコードなのか、それともデータファイルなのか」という疑問を抱いていてまずはここの理解に努めた。結論としてモデルの構造（768次元の入力を1次元の数値へ変換する数式）は「コード」であり、学習によって最適化された重みパラメータが「データ（safetensorsファイル）」という理解に至った。

モデルを開発するための事前理解をした上で、本プロジェクトでは開発環境の役割分担を明確に切り分けた。

 * 特徴量の抽出（Mac）: Swiftを用いてDINOv3からEmbeddingを一括抽出し、CSVデータセットとして保存。
 * モデルの訓練（Mac）: PythonおよびMLXを用いて線形モデルの教師あり学習を実施。
 * アプリでの推論（iPhone/iPad）: 訓練完了した重み（safetensors）をSwiftアプリへ読み込み、高速推論を実行。

まず学習もSwiftですべきか、それともPCでMLXで実施すべきかを切り分けた。切り分ける上でまずはEmbeddingのデータセットについて調査したが、一般的な公開データセットでは利用者がどの基底モデルを使うか分からないため、Embedding自体を配布することは稀とのことだった。しかし本アプリのように「DINOv3を特徴抽出器として固定する」と決めている場合、画像そのものではなく事前に抽出したEmbeddingを教師データとして学習を回すアプローチが有効と判断した。そのため手元のPCで利用できるものであって数秒で学習が完了するMLXでの学習を採用し、SwiftはiPhone/iPadでの推論(戦闘力表示)に使う、という分担にした。

## 訓練時と推論時の特徴量抽出について

### 通常の物体検出と今回のアプリに組み込んだ特徴量抽出の違い

DINOv3のようなVision Transformerモデルにおいて、出力されるCLS（Classification）トークンは基本的に「画像全体を代表する特徴量（Embedding）」として機能する。通常の用途では入力写真全体の特徴をこの1つのベクトルに集約して推論などに用いるものである。要するに通常、この写真全体の特徴量を取得するものである。

**[訓練用写真](../../resources/origin.png)**

しかし、今回のスカウターアプリでは「写真の背景」などに推論結果が左右されないように、特徴量抽出のパイプラインに大きな工夫を組み込んだ。具体的には、AppleのVision Frameworkを用いて画像を事前に解析し、人物領域だけを正確に切り抜いた状態の画像をDINOv3へと入力している。下記のフローの通りだ。

```text
写真
 ↓
人物切り抜き
 ↓
DINOv3
 ↓
CLS Token
 ↓
Linear回帰モデル
 ↓
戦闘力（Power）
```

この独自のパイプラインにより、画像全体ではなく「人物そのもの」に焦点を当てた純度の高いEmbeddingを抽出することが可能となった。イメージでいうとこの画像の赤枠で囲った内側のEmbeddingの抽出である。

### 訓練時と推論時の画像不一致という課題

訓練プロセスを進める中で、課題となったのが「訓練画像と推論時画像の前処理の不一致」だった。

当初、収集した人物画像をそのままDINOv3に入力し、抽出されるEmbeddingが生成されたCSVを作成していた。要は図の状態のものである。

**[検出範囲を示す図](../../resources/mantracking_old.png)**

しかし、このCSVのデータを元に学習した重みをiOSアプリに組み込んで実機テストを行ったところ、推論されて表示される戦闘力が訓練時の想定と大きく乖離してしまうことがわかった。

原因を調査したところ、iOSアプリ側で本家に近づけるために推論前にスカウター演出として「背景を薄黄色にし、人物を黄土色に塗りつぶす」という画像エフェクトを施しているためだった。DINOv3のような高感度なVision Transformerは、色調やコントラストの変化に対して非常に敏感であり、「素の写真」で学習したモデルに対して実際のコードでは「黄土色に着色された写真」が入力されるため、特徴量空間内でベクトルがズレてしまい、正しいスコアが出力されなくなっていた。流石に物体検出や分類タスクに使われるモデル、と関心した点である。

このズレの課題を解決するため、Macで実行する学習用の特徴量抽出ツール（Swift）においても、iOS実機と全く同じ色付け・切り抜きフィルタを適用した画像からEmbeddingを生成するようにパイプラインを改修した。前処理の条件を完全に一致させたことで、実機上でも安定した戦闘力判定が得られるようになった。要するにこういった加工を写真に施し、この状態のEmbeddingを生成するコードを作り、これを訓練に用いるようにした。

**[アプリ実行時、解析中の画像](../../resources/mantracking.png)**

## 訓練用画像データとEmbedding抽出アプリの作成

訓練用のデータセットとして、Hugging FaceやKaggle等のオープンデータセット、そして自分の写真から、多様な体型・姿勢の人物画像（全身および上半身）を収集した。

さらに、iOSアプリと全く同一の条件で特徴量を抽出するため、macOSネイティブで動作する「特徴量抽出ツール」をSwiftで作成した。内容は元々のスカウターアプリの実装フローのCLS token取得まで同じとした上で、画像を選ぶことでその画像のembeddingをcsvファイルとして取得できるようにしたものだ。このembeddingに加えて、idと戦闘力となるpowerの数字を加えたcsvファイルを使って学習を進めることにした。画像認識の分野では画像そのものを学習させることも多いが、本プロジェクトのように特徴量を抽出するモデルが決まっている場合はこのアプローチが効率的なようだ。

### macOS向けコードへの移植とデータセット運用

学習用のEmbeddingデータ抽出のため、iOSアプリ用に作成したVisionPipelineやImagePreprocessorをmacOS向けに移植した。主な変更点は以下の通り。

 * UIKit依存の排除: UIImageからNSImageへの置き換え。
 * セグメンテーションの統一: iOS側と同一のスカウター加工を施してテンソル変換。
 * CSVExporterの実装: 画像群から抽出した768次元ベクトルをembedding.csvとして出力し、ラベル側のpower.csvと突合。

Python側でのデータ加工においては、CSVの特定カラムに値をbackfill（穴埋め）してデータセットを拡充するなど、柔軟なデータハンドリングを行った。また、同じ人物を撮影角度や距離を変えて10枚撮影し、Vision Frameworkでの切り抜き有無によってCLSトークンのコサイン類似度がどれほど安定するかを比較検証し、切り抜き処理が特徴量の安定化に不可欠であることを実証した。

## 線形回帰（Linear Regression）の学習

ここから学習の詳細に入る。収集した特徴量CSVを使い、戦闘力予測モデルの学習を行った。

モデルの数式は非常にシンプルなもの。

```text
y = x · W + b
```

ここで、xはDINOv3が出力した768次元のEmbeddingベクトル、Wは学習対象となる768個の重みパラメータ、bはバイアス（オフセット）、そしてyが推定戦闘力（今回は1〜99の範囲で設定）だ。

### 損失関数の選択 ── MSE LossとHuber Loss

学習プロセスにおける損失関数の選択は、モデルの振る舞いに直結する重要な判断である。最初に採用したのは、回帰タスクで最も代表的な平均二乗誤差（MSE Loss）であった。

MSE Lossは計算がシンプルで微分も容易だが、一つ重大な弱点がある。誤差を二乗するため大きな外れ値が一つでも含まれると、その一件にモデル全体が引っ張られてしまうからである。

本プロジェクトのデータセットは、最初一般的な体格の人物が大多数を占め、Powerが高いアスリート体型のサンプルが極めて少数という偏った分布であった。MSEではこの少数の高Powerサンプルの大きな誤差がペナルティとして支配的になり、中間層のPower帯の予測精度が犠牲になる傾向が見られた。

そこで比較検討したのがHuber Lossである。Huber Lossは、誤差が小さいときはMSEのように二乗ペナルティを与え、誤差が大きいときはMAE（平均絶対誤差）のように線形ペナルティに切り替わるハイブリッド関数である。閾値（デルタ）を境に振る舞いが変わるため、「その一件は確かに間違っているが、モデル全体をそこに引っ張らせない」という動きをする。

同じデータセットで両者を比較した結果、Validation Lossの絶対値はそのままでは比較できないものの、予測値そのものが目に見えて改善した。MSEでは教師データがPower 5の人物に対して2.5〜3.2といった大幅に外れた予測が多発していたが、Huber Lossに切り替えたところ、同じ人物に対して4.2〜5.4と教師値の近傍に収束するようになった。以降の訓練ではHuber Lossを標準の損失関数として採用した。

### 学習ループの実装

MLXによる学習ループの全体像を示す。PythonのMLXフレームワークはNumPyライクなAPIを持ちながら、Apple Siliconのユニファイドメモリを活かした高速な勾配計算を提供する。以下は学習ループ部分のサンプルコードとなる。

**train_loop**

```python
import mlx.core as mx
import mlx.nn as nn
import mlx.optimizers as optim

model = nn.Linear(768, 1)
learning_rate = 0.001
optimizer = optim.Adam(learning_rate=learning_rate)

def huber_loss(pred, target, delta=1.0):
    diff = mx.abs(pred - target)
    return mx.mean(
        mx.where(diff < delta,
                 0.5 * mx.square(diff),
                 delta * (diff - 0.5 * delta))
    )

def loss_fn(model, x, y):
    pred = model(x)
    return huber_loss(pred, y)

loss_and_grad_fn = nn.value_and_grad(model, loss_fn)

for epoch in range(100):
    loss, grads = loss_and_grad_fn(model, X_train, y_train)
    optimizer.update(model, grads)
    mx.eval(model.parameters(), optimizer.state)
```

nn.value_and_gradは、損失値と勾配を一度の前向き・後ろ向き計算で同時に取得する関数である。学習率のコントロールを行うオプティマイザにはTransformerの学習でよく使われるAdamを採用し、重み減衰（Weight Decay）によるL2正則化を通じて過学習の抑制を図った。MacBook Air（M1, 8GB）上での学習時間は、1,000サンプル・200エポックの場合でも数秒程度で完了する。

### Learning Rateの影響 ── 学習率の違いによる差異について

ハイパーパラメータの中でも、Learning Rate（学習率）はモデルの収束挙動に最も大きな影響を与えるものである。実際の訓練で、Learning Rate 0.01と0.001を比較した結果は非常に示唆に富むものだった。

Learning Rate 0.01の場合、Train Lossは100エポックで0.03まで急速に下がった。しかしValidation Lossは30エポック付近の0.94を底にして以降は上昇を続け、最終的に1.14に達した。一方、Learning Rate 0.001の場合、Train Lossの低下は穏やかで100エポックで0.27であったが、Validation Lossは0.83で安定した。

**Learning Rateによる訓練結果の比較**

| Learning Rate | Train Loss（100epoch） | Val Loss（100epoch） |
| :--- | :--- | :--- |
| 0.01 | 0.03 | 1.14 |
| 0.001 | 0.27 | 0.83 |

ここで学んだ重要な教訓がある。Train Lossを下げることは目的ではない。Train Lossは「モデルが訓練データをどれくらいうまく説明できているか」を表しているに過ぎず、最終的に必要なのは「初めて見る写真をどれくらいうまく予測できるか」、つまりValidation Lossの低さだ。Train Lossが極端に低いのにValidation Lossが高い状態は、典型的な過学習（Overfitting）になる。

### 過学習との闘い ── 最適なEpoch数の探索

学習データへの適合度を高めようとエポック数を増やすと、必ずどこかでValidation Lossが底を打ち、上昇に転じる。この分岐点を見極めることが訓練の鍵だと認識した。

下記は実際にデータセットを拡充した1,234サンプルでの訓練結果の一例である。

```text
Epoch  80, Train Loss: 1.1623, Val Loss: 1.6088
Epoch  90, Train Loss: 1.1092, Val Loss: 1.5982
Epoch 100, Train Loss: 1.0649, Val Loss: 1.5912
Epoch 110, Train Loss: 1.0272, Val Loss: 1.5840
Epoch 120, Train Loss: 0.9949, Val Loss: 1.5799
Epoch 130, Train Loss: 0.9675, Val Loss: 1.5783
Epoch 140, Train Loss: 0.9440, Val Loss: 1.5783
Epoch 150, Train Loss: 0.9236, Val Loss: 1.5788
```

Train Lossは一貫して減り続けているが、Validation Lossはエポック130〜140で底を打ち、150以降はわずかに上昇し始めている。この「Val Lossが最小となるエポック」が、モデルの汎化性能が最も高い地点である。最終的にはこのBest Epochの重みをpower_predictor.safetensorsとして保存する運用とした。

さらにエポック数を1,000まで引き上げた実験では、過学習の危険性がより明確に現れた。Train Lossは30.9まで低下する一方、Validation Lossは30.6にとどまるどころか上昇を続け、予測値にはマイナス値（-7.4、-76.9など）が出現する始末だった。エポック数は「多ければ多いほどよい」わけではなく、適切な打ち切りが不可欠であることを身をもって体験した。

### データセット育成 ── モデルを良くする前にデータを良くする

訓練を繰り返す中で最も効果的だった改善策は、モデルの複雑化（MLP化など）ではなく、データセットの質と量の向上であった。

初期段階では自分だけのデータを用いた訓練を行い、Power 5の予測は4.2〜5.7の範囲に収まるなど手応えを得た。しかし、オープンデータセットを含めて多くのサンプルに拡充したところ、Validation MAEは1.99と、まだ改善の余地がある数値であった。

ここで導入したのが、Power帯ごとのMAE（平均絶対誤差）分析である。

```text
Power  4 : Samples= 66, MAE=1.4842
Power  5 : Samples= 50, MAE=1.5099
Power  6 : Samples= 38, MAE=1.8787
Power 10 : Samples= 19, MAE=3.0647
Power 15 : Samples=  4, MAE=5.1857
```

この分析から、サンプル数が少ないPower帯ほどMAEが大きい傾向が明確に読み取れた。モデルの能力不足ではなく、学習データの偏りが予測精度を律速しているのである。

この気づきから、データ収集の戦略を「とにかく枚数を増やす」から「不足しているPower帯を重点的に補う」へ転換した。また、同一人物であっても撮影条件を意図的に変えて（横向き、距離違い、腕位置違い、鏡越し、スマートフォン保持、少ししゃがんだ姿勢、照明違い）バリエーションを増やすことで、モデルの汎化性能を高める方針を取った。

### 最初の実機確認 ── 手応えと新たな課題

学習した重みをiOSアプリに搭載し、実機で確認した結果は以下の通りであった。

 * データセットに含まれる全身写真と同様の条件で撮影すると、Power 5付近を推移する。
 * 半身だけが写った状態では、Power 2.5前後まで低下する。
 * iPadを持ったまま鏡で測定すると、Power 4前半を推移する。

全身の写り込み比率や撮影条件がスコアに大きく影響することが実機ベースで確認できた。DINOv3のEmbeddingが基本的に「画像全体」を理解する汎用視覚特徴であるがゆえに、人物だけ画像であっても向きやポーズや画像の写り込みの割合でスコアが大きく変動するという気づきを得た。

この結果は、前章で述べたVision Frameworkによる人物切り抜き処理の重要性を改めて裏付けるものであった。切り抜きによって背景を除去し、人物領域を正規化した上でEmbeddingを生成することが、安定した戦闘力予測の前提条件であることを実運用の中で実証した。

### safetensorsの書き出しとアプリへの統合

最終的にValidation Lossが最小となったepochの重みパラメータを、power_predictor.safetensorsとして書き出し、戦闘力モデルとしてMLX Swiftに実装しiOSに組み込んで使うことにした。このファイルサイズはわずか数KBである。768個の重みパラメータと1個のバイアス、合計769個の浮動小数点数を格納しているに過ぎない。

この軽量なsafetensorsファイルをiOSプロジェクトのバンドルへコピーすることで、DINOv3の高度な視覚理解力と、独自データによる特化型スコアリングが融合した「スカウター」の頭脳が完成する。訓練のサイクルは「データ収集 → Embedding抽出 → MLXで学習 → safetensors書き出し → アプリに配置」というシンプルな流れであり、MacBook一台で何度でも回せる軽量さが、最大の利点と考えている。
